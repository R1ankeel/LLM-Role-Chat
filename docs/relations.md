# Система отношений

Система моделирует **направленные** отношения между персонажами: `source → target`. Отслеживаются только рёбра **NPC → NPC** и **NPC → Player**; рёбра Player → NPC не хранятся (миграция удаляет legacy-строки). Игрок — валидная *цель* (боты → игрок), но никогда не *источник*.

Разделение ответственности:
- **Хранилище** (`relationship_service.py`): CRUD, применение дельт, open issues, салиентность.
- **Интерпретатор** (`relationship_interpreter.py`): детерминированный перевод чисел → семантические ярлыки. Без БД, без LLM.
- **Анализатор** (`relationship_analyzer.py`): LLM-предложения дельт (batch / per-pair).
- **Интеграция** (`chat_engine.py`): построение контекста, evidence-gating, инвокация анализатора, тик салиентности.

## §1. Проблема

Сырые числовые метрики, вставленные в промпт персонажа, дают три проблемы:
1. **Семантический шум** — модель видит числа и «интерпретирует» их нестабильно.
2. **Загрязнение знаний** — персонаж «знает» чужие внутренние числа о себе.
3. **LLM-галлюцинации** — модель сама решает, как изменилось отношение, без evidence.

## §2. Решение

Два пути данных:

```
               ┌──────────────┐   LLM-анализ   ┌────────────────┐
  раунд игры ──┤ chat_engine  ├───────────────►│  анализатор    │
               └──────────────┘                │  (batch/per)   │
                                               └───────┬────────┘
                                                       │ deltas
                                               ┌───────▼────────┐
                                               │ evidence-gate │  ← детерминированный §8.3
                                               └───────┬────────┘
                                                       ▼
                                               ┌────────────────┐
                                               │  apply_delta   │  ← кламп, граф переходов, события
                                               └────────────────┘
```

Промпт персонажа строится **интерпретатором**: числа → ярлыки → фразы. Модель никогда не видит raw-метрики.

## §3. Модель состояния

`character_relationships` — направленное ребро `source_character_id → target_character_id`:

| метрика | диапазон | дефолт |
|---|---|---|
| `affection` (привязанность) | 0–100 | 50 |
| `trust` (доверие) | 0–100 | 50 |
| `attraction` (влечение) | 0–100 | 0 |
| `resentment` (обида) | 0–100 | 0 |
| `jealousy` (ревность) | 0–100 | 0 |
| `relationship_type` | из валидного списка | `нейтральное` |

**Reciprocity без синхронизации (Sprint 2 item 11):** рёбра направленные,
автоматическое зеркалирование запрещено. `A→B` и `B→A` — независимые строки
(`UNIQUE (source_character_id, target_character_id)`); создание/дельта/PUT трогают
только указанное ребро и никогда обратное, поэтому валидно `A→B: affection=90`,
`B→A: affection=20` (односторонняя любовь, страх и т.д.). `get_or_create_relationship`
отклоняет self-loop (`source == target`). Инвариант зафиксирован тестами
`tests/test_relationship_reciprocity.py::TestReciprocityNoSync`.

Плюс `description` (текущее), `initial_description` (исходное для диффа). Метрики клампаются в 0–100 (`clamp_metric`); дельты клампаются в ±`RELATIONSHIP_MAX_DELTA` (20).

Валидные типы (19): `нейтральное, друг, близкий_друг, лучший_друг, союзник, верный_союзник, соперник, враг, заклятый_враг, симпатия, романтика, возлюбленные, наставник, ученик, семья, родитель, брат_сестра, незнакомец, знакомый`.

Переходы между типами — **граф** `relationship_transition_rules` (config.py:174): смена типа разрешена только по рёбрам графа, иначе `apply_delta` сохраняет старый тип (лог-предупреждение).

## §4. Интерпретатор: состояние → семантические ярлыки

`interpret(rel, open_issues)` — чистая функция, пороги заданы константами:

| ярлык | правило |
|---|---|
| `trust` | low < 30, medium 30–69, high ≥ 70 |
| `attachment` | low < 40, medium 40–69, high ≥ 70 |
| `hostility` | high если resentment ≥ 50 или jealousy ≥ 60 |
| `attraction` | `hidden` если attraction ≥ 70 и (resentment ≥ 50 или trust < 40); `visible` если ≥ 40; иначе `none` |
| `jealousy` | none < 30, moderate 30–59, high ≥ 60 |

**Производные комбинации** (сильнее базовых ярлыков, тон-нейтральные):
- `болезненная привязанность` — affection ≥ 70 и trust < 40;
- `скрытое влечение` — attraction ≥ 70 и (resentment ≥ 50 или trust < 40);
- `недоверие + обида` — trust < 30 и resentment ≥ 50;
- `открытый вопрос` — на ребре есть open issues (не читая их текст, §7.3).

Ярлыки намеренно описывают *что* персонаж чувствует, а не *как* это выражает (экспрессия — работа карточки личности, §15). Нейтральные значения не генерируют фраз — свежий нейтральный отношения становится одной строкой `Имя: нейтральное` без ложных сигналов.

## §5. Форматирование для промпта (без чисел)

`format_interpretation(interp, target_name)` собирает естественные фразы-тенденции:

```
Борис: друг
  Ты доверяешь Борису.
  Ты помнишь обиду на Бориса и склонен возвращаться к причине конфликта.
  Между тобой и Борисом остался нерешённый вопрос, и ты к нему мысленно возвращаешься.
  описание: <description>
  - <последние события>
```

Имена склоняются best-effort (`decline_name`): дательный/винительный падеж для однословных имён; имена на `-ь`, многословные и гласные возвращаются без изменений.

Блок отношений (`build_relationships_block`) — по всем исходящим рёбрам персонажа, каждое с последними событиями (`RELATIONSHIP_MAX_EVENTS_IN_PROMPT`=5) и open issues.

## §6. Якорь раунда

`round_id = f"r{chat_id}-m{user_message.id}"` — стабильный идентификатор одного раунда, вычисляется один раз на `process_user_message_streaming`. Используется в `relationship_events.source_round_id`, `relationship_issues.created/resolved_round_id`, `last_mention_round_id` и в тике салиентности. Позволяет связать изменения отношений и issues с конкретным сообщением пользователя.

## §7. Open issues (сюжетные крючки)

### §7.1 Типы
Whitelist из 10 типов (`schemas.IssueType`), никогда не свободная строка: `broken_promise, debt, unfulfilled_request, lie, unresolved_conflict, suspicion, hidden_secret, missing_apology, unreturned_favor, emotional_grievance`.

### §7.2 Создание/резолв
`create_issue` отбрасывает issue если:
- неизвестный `issue_type` (не в whitelist);
- текст не прошёл `sanitize_issue_text` (см. §14);
- `importance < RELATIONSHIP_MIN_IMPORTANCE` (3);
- near-дубликат открытого issue того же типа на этом ребре (Jaccard ≥ `RELATIONSHIP_ISSUE_NEAR_DUP_JACCARD`=0.7).

`resolve_issue` — только если issue принадлежит **этому** ребру (`relationship_id` совпадает); служба никогда не угадывает пару по тексту. `apply_issue_deltas` — парная атрибуция обязательна: source/target каждого issue должны совпадать с ребром, иначе действие отклоняется.

Issues применяются **вне зависимости** от важности метрических дельт — у каждого issue свой importance-гейт.

### §7.3 Текст — данные, не инструкция
Поле `text` — это факт/данные сцены, а не инструкция для LLM (§14): ограничено `RELATIONSHIP_ISSUE_TEXT_MAX`=200 символов, очищено от управляющих символов и маркеров prompt injection. Интерпретатор не читает текст issue — только наличие (`open_issues` truthy → производный ярлык `открытый вопрос`). Полный текст попадает в контекст только в отдельном data-блоке `build_open_issues_block`.

### §7.4 Детерминированная салиентность
Счётчик `rounds_since_last_mention` на issue:
- тик `tick_open_issues` раз в раунд: неупомянутые issues `+=1`, упомянутые — сброс в 0 (`touch_issue`). Issues, созданные в этом же раунде, остаются на 0 до следующего.
- «упомянуто» = передано анализатору для своей пары **или** отобрано в `<open_issue data>` блока контекста источника.

Проактивный буст `proactive_boost_from_issues` — **взвешенный**, запрет `const * len(open_issues)` (три мелких крючка не должны весить как один крупный конфликт):

```
salience_i = clamp01(1 - rounds_since_last_mention_i / DECAY_ROUNDS)   # DECAY_ROUNDS=5
w_i        = (importance_i / 10) * salience_i
boost      = clamp(COEFF * sum(w_i), 0, BOOST_CAP)                     # 0.15, cap 0.35
```

Детерминированный: одинаковый вход → одинаковый выход.

## §8. LLM-анализатор

`ANALYSIS_TEMP = 0.3`. Модель анализатора — `RELATIONSHIP_ANALYZER_MODEL` или модель чата.

### §8.1 Batch-режим (по умолчанию)
Один LLM-вызов на все пары с evidence (вместо per-pair O(N²)). Возвращает `(deltas, orphan_issues)`:
- каждый delta/issue несёт свои source/target id;
- пары вне `known_pairs` отбрасываются — анализатор не может выдумать или подменить пару;
- issues для ребра без метрической дельты возвращаются отдельно (`orphan_issues`) и применяются без касания метрик/типа ребра.

### §8.2 Промпт
- **§8.2.1** — карточка персонажа (id), текущие метрики и тип, недавние события, известные open issues (id + тип + текст), сжатая выжимка раунда по паре (`excerpt`), правила evidence-gating.
- **§8.2.2** — общая «социальная сцена» (`_build_batch_scene_summary`): кто где, кто кому что сказал (global view), до 30 строк.

### §8.3 Evidence-gating (детерминированный)
`_evidence_mode(pair_ctx)` → `direct | observed | none`, вычисляется из `_build_pair_relationship_context`:
- `direct_interaction` — source обратился к target напрямую (адресация/со-присутствие), либо target говорил напрямую source'у; со-присутствие двоих (`only_two_present`) приравнивается к direct.
- `observed_target` — source воспринимал поведение target (присутствовал при чужих репликах о target, слышал target при не-absent presence).
- `none` — нет воспринимаемых свидетельств.

`_constrain_pair_delta`:
- mode `none` → **REJECT** (None): нет evidence — нет права менять; LLM не решает допустимость.
- mode `direct` → дельты уже клампнуты схемой в ±20; тип может меняться (граф проверяет `apply_delta`).
- mode `observed` → дельты ограничены `RELATIONSHIP_REFLECTION_DELTA_CAP`=5, тип заморожен (если `RELATIONSHIP_TYPE_CHANGE_REQUIRES_INTERACTION`=true).

### §8.4 Fallback
При сбое batch (`BatchAnalysisError`) → per-pair анализатор `analyze_relationships`, если `RELATIONSHIP_BATCH_FALLBACK=true`. Fallback **никогда** не отключает evidence-gating. При выключенном fallback — отношения пропускаются (лог).

## §9. Применение дельт (`apply_delta`)

1. `get_or_create_relationship` — ребро гарантированно существует.
2. Issues применяются первыми (каждое со своим гейтом).
3. Если `importance < RELATIONSHIP_MIN_IMPORTANCE` → метрики не трогаются (issues уже применены).
4. Проверка перехода по графу; дельты клампятся в ±20, метрики в 0–100.
5. `update_description` — только если true и есть текст.
6. Если итог идентичен текущему состоянию — запись не делается, событие не создаётся.
7. Иначе создаётся `relationship_events` (с дельтами, reason, importance, `source_round_id`) и коммит.

## §10. Epistemic mask (Sprint 2 item 10)

Персонаж «знает», как к нему относится другой, **только** когда был прямой/наблюдаемый evidence поведения этого другого в текущем раунде (`_compute_epistemic_evidence` → `_evidence_mode != "none"`). Блок `<epistemic_mask>` для смотрящего персонажа (цель входящих рёбер):
- рёбра с evidence — интерпретация **без чисел** (`format_interpretation_from_other`): `Известное тебе отношение X к тебе: …`;
- рёбра без evidence — явно `Тебе неизвестно, как X относится к тебе.`;
- чужие внутренние метрики никогда не попадают в промпт;
- лимит строк — `RELATIONSHIP_EPISTEMIC_MAX`=8.

## §11. Behavior drivers (Sprint 1 items 3–4)

`weighted_behavior_drivers` — ранжированные (вес, тенденция) пары по одному ребру. Веса стабильны между рёбрами (сравнимы на единой шкале). Производные комбинации весят больше базовых: болезненная привязанность=6, недоверие+обида=6, скрытое влечение=5, открытый вопрос=5; затем trust low/hostility/jealousy high=4, attachment=3, attraction visible/jealousy moderate=2, trust high=1.

`build_behavior_drivers_block` агрегирует по всем исходящим рёбрам персонажа, сортирует по убыванию веса и берёт top-K (`RELATIONSHIP_DRIVERS_MAX`=4) в блок `<behavior_drivers>…</behavior_drivers>`. Тенденции — описание чувств, никогда не команды (нет «должен/обязан»).

## §12. Типы и переходы

Граф переходов в `config.py` (`relationship_transition_rules`). Примеры: `нейтральное → друг/союзник/симпатия/соперник/знакомый/незнакомец`; `враг → заклятый_враг/соперник/нейтральное`; `симпатия → романтика/возлюбленные/друг/нейтральное`. Смена типа всегда через `apply_delta` с валидацией; при невалидном переходе тип сохраняется.

## §13. Журнал событий

`relationship_events` пишется при каждом реальном изменении (см. §9). `get_recent_events` (до `RELATIONSHIP_MAX_EVENTS_IN_PROMPT`) фидаются в промпт персонажа и анализатора.

## §14. Prompt-injection защита (текст issue)

Текст issue — LLM-продукт, который позже попадает в контекст другого LLM. Поэтому:
- `sanitize_issue_text`: нормализация пробелов, удаление управляющих/непечатных символов, обрезка до `RELATIONSHIP_ISSUE_TEXT_MAX`, и **отклонение** при маркерах-инструкциях: `игнорируй, игнорировать, ignore, system:, developer:, забудь предыдущие`;
- блок `<open_issue data>` — только данные (`build_open_issues_block`, до `RELATIONSHIP_MAX_ISSUES_IN_PROMPT`=3), никогда инструкция;
- интерпретатор опирается на наличие issue, а не на текст.

## §15. Границы ответственности

- Интерпретатор выдаёт *что* персонаж чувствует (ярлыки/тенденции).
- *Как* это выражается — задача карточки личности в системном промпте.
- Анализатор может *предлагать*; всё решают детерминированные гейты (§8.3) и валидации (§7.2, §9).
