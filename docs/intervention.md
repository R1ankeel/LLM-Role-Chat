# Вмешательство (одноразовая инструкция для следующего хода)

Механизм, позволяющий игроку дать **одноразовое указание**, которое применяется
только к ближайшей генерации (следующему ходу) и автоматически исчезает после
успешного раунда.

## Адресность (получатели)

Каждое вмешательство имеет **явный список NPC-получателей**, который
фиксируется **в момент создания** и не пересчитывается при генерации. В промпт
конкретного NPC попадают только те вмешательства, чей замороженный набор
содержит его `character_id`. Фильтрация идёт **до формирования prompt**, по ID
персонажа, без имён и без LLM.

Получатели определяются при создании:

- **Явный список** (`recipient_character_ids`) — только указанные NPC (из этого
  чата);
- **Пустой/отсутствующий список** — детерминированно по локации игрока: каждый
  NPC, находящийся в той же локации, что и игрок, становится получателем.
  Сравнение локаций переиспользует канонические правила восприятия
  (`perception.same_location_identity`: `location_id` при наличии с обеих
  сторон, иначе нормализованные строки; пустая строка — общая сцена, которая
  совпадает только с общей сценой).

Это гарантирует, что **поздно прибывший NPC не узнает старое вмешательство**:
набор получателей заморожен на момент создания и не пересчитывается, даже если
персонаж пришёл в локацию позже или генерация упала.

## Принцип работы

- Инструкция хранится в таблицах `interventions` / `intervention_recipients` и
  никогда не попадает в таблицу `messages`. После **полностью успешного** раунда
  перед потреблением инструкции в память каждого получателя записывается
  **незаметный факт** вида «Игрок попросил: …» (категория `событие`,
  `memory_type=episodic`, `importance=0.9`, без `source_message_ids`, чтобы факт
  не был отфильтрован witness-фильтром для персонажей, не воспринявших реплики
  раунда). Слово «вмешательство» в факте не используется — он читается как
  обычное событие истории, чтобы затронутые боты не «теряли» контекст на
  следующих ходах. Факт пишется **только получателям**.
- `character_id` в схеме — legacy-маркер области действия (`None` = chat-wide);
  **источник истины о том, кто слышит инструкцию — таблица `intervention_recipients`**.
- В промпт блок внедряется **сразу перед generation cue** (и в chat-режиме, и в
  generate-режиме), как высокоприоритетная директива текущего хода.

## Состояния

```
нет инструкции -> создана -> ожидает генерации -> использована -> удалена
```

- **Создана**: `PUT /chats/{id}/intervention` (+ получатели).
- **Ожидает генерации**: инструкция переживает перезагрузку страницы и ошибки
  генерации.
- **Использована**: после **полностью успешного** раунда (ни один персонаж не
  упал в fallback «*[X молчит, не в силах ответить]*»). Потребление
  защищено identity-проверкой: каждая инструкция удаляется по своему `id` из
  снапшота раунда, поэтому новая инструкция, созданная во время генерации,
  переживает её.
- **Удалена**: автоматически после использования или вручную игроком
  (`DELETE /chats/{id}/intervention`).
- При ошибке генерации, остановке или разрыве SSE-соединения инструкция
  **сохраняется** для повторной попытки (вместе с замороженными получателями).
- Перегенерация ответа («Повторить ответ») **применяет** инструкцию к
  перегенерируемому персонажу, если он — получатель, но **не потребляет** её.

## HTTP API

| Метод | Путь | Тело | Ответ |
|-------|------|------|-------|
| `PUT` | `/api/chats/{chat_id}/intervention` | `{"instruction": "...", "recipient_character_ids": [..]}` | `InterventionRead` (200) |
| `GET` | `/api/chats/{chat_id}/intervention` | — | `InterventionRead \| null` (200) |
| `DELETE` | `/api/chats/{chat_id}/intervention` | — | `204` |

Схема `InterventionRead`: `chat_id`, `character_id` (legacy, пока `null`),
`instruction`, `created_at`, `recipient_character_ids`. Пустая/пробельная
инструкция отклоняется (422/400), чат должен существовать (иначе 404),
неизвестные получатели (не NPC этого чата) отклоняются (400). Если список
получателей пуст/не передан — вычисляется из локации игрока (см. выше).

## Промпт

Шаблон `intervention.block` в `app/prompts/ru.json` оборачивает текст в
`<intervention>…</intervention>` и явно указывает модели:

- действует **только на этот ответ/ход**;
- сохранять характер, стиль, личность, правила мира и логику сцены;
- не упоминать механизм вмешательства, не обращаться к нему как к реплике и не
  добавлять в память/историю.

Вмешательства не передаются всем NPC «с инструкцией игнорировать»: per-NPC текст
директивы строится на backend (`build_directive_for_character` /
`build_directives_map`) и в промпт попадает только получателю.

## Код

- `app/models/intervention.py` — ORM `Intervention` / `InterventionRecipient`.
- `app/crud/interventions.py` — CRUD: replace-семантика по `(chat_id, character_id)`,
  получение с eager-load получателей, потребление по id.
- `app/pending_intervention.py` — жизненный цикл + per-NPC фильтрация
  (`build_directive_for_character` / `build_directives_map`) + детерминированный
  подсчёт получателей по локации (`compute_default_recipients`).
- `app/schemas/` — `InterventionCreate`, `InterventionRead`.
- `app/routers/chat_engine.py` — эндпоинты PUT/GET/DELETE (PUT вычисляет
  получателей по локации, когда список не передан).
- `app/prompt_builder.py` — `build_intervention_block(text)`.
- `app/pipeline/streaming.py` — снапшот вмешательств в начале раунда, per-NPC
  директивы, потребление по id в конце успешного раунда.
- `app/pipeline/regeneration.py` — чтение директивы без потребления (только для
  получателя).
- `frontend/src/stores/intervention.ts` + `frontend/src/api/intervention.ts` —
  состояние и API Vue-клиента; UI кнопка/бейдж «⚡ Вмешательство» в
  `Composer.vue`, обновление при открытии чата и после раунда.
